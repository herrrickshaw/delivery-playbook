Lineage

Every model on this page exists because the one before it broke down somewhere specific. Reading them in order tells you more than reading any one in isolation.

1970
Waterfall
Royce formalizes sequential phases — then spends the rest of the paper warning against running it without feedback loops.
1988
Spiral
Boehm adds risk analysis loops on top of waterfall for projects where the unknowns are the danger.
1995
Scrum
Schwaber & Sutherland formalize timeboxed sprints and inspect-adapt cadence.
1999
XP
Beck pushes engineering discipline — TDD, pairing, CI — to the center of the process.
2001
Agile Manifesto
17 practitioners name the shared values under Scrum, XP, Crystal, and the rest.
2007
Kanban (software)
Anderson adapts Toyota's pull system for flow-based, non-iterative work.
2009
DevOps
Debois coins the term; Flickr's "10+ deploys a day" shows continuous delivery at scale.
2011
Lean Startup / SAFe
Ries applies build-measure-learn to product risk; SAFe attempts to scale agile across whole organizations.
2014
DORA metrics
Forsgren's research gives delivery performance four measurable signals instead of opinions.
01

Classic SDLC models

Plan-driven models treat the requirement as knowable in advance and optimize for getting it right the first time. They still run the world in aerospace, medical devices, and anywhere a mistake is expensive to unwind.

ModelShapeBest fitKey artifactWhere it breaks
Waterfall One pass: requirements → design → build → verify → maintain Fixed, well-understood scope; contractual or regulated delivery Signed-off requirements specification Misunderstandings surface at acceptance, not at week two
V-Model Waterfall with each build phase mirrored by a test phase Safety-critical systems — medical, automotive, aerospace Requirements-to-test traceability matrix Verification-heavy; still can't absorb a changed requirement mid-flight
Incremental Deliver in functional slices, each its own mini-waterfall Large systems where the core is known but can be sequenced Prioritized increment roadmap Weak upfront architecture makes late increments expensive to bolt on
Spiral Repeated loops of plan → assess risk → prototype → evaluate Novel, high-cost, high-risk builds needing real prototyping Risk register, updated every loop Formal risk analysis overhead crushes momentum on ordinary projects
RAD Heavy prototyping with continuous user feedback, light planning UI-heavy apps, tight deadlines, an engaged user in the room Evolving working prototype Thin on architecture discipline — punishing for large or long-lived systems
02

The Agile family

Agile methods treat the requirement as unknowable in advance and optimize for shortening the feedback loop instead. They trade upfront certainty for the ability to change direction cheaply.

ModelShapeBest fitKey artifactWhere it breaks
Scrum Fixed-length sprints; PO/Scrum Master/dev team; planning, daily, review, retro One product team with priorities that shift, but not daily Sprint backlog & burndown "Zombie Scrum" — ceremonies run on autopilot, nothing actually inspected
Kanban Continuous pull-based flow, explicit WIP limits, no fixed iteration Support, ops, and maintenance work of unpredictable size Board + cumulative flow diagram Without enforced WIP limits it's just a to-do list, and throughput collapses
XP Pair programming, TDD, continuous integration, collective code ownership Teams needing high code quality against changing requirements A passing automated test suite as the living spec Practices adopted without the discipline — tests written after the fact — become theater
Lean / Lean Startup Eliminate waste; validate the riskiest assumption with the smallest experiment High-uncertainty, pre-product-market-fit stage Validated-learning log from each MVP experiment "MVP" quietly becomes the permanent, never-polished product
Crystal Family of lightweight methods, scaled by team size and criticality Small, co-located, trusted teams Reflection-workshop notes Under-specified once the team is distributed or grows past ~8
SAFe / LeSS Shared cadence across many teams — PI planning, Scrum of Scrums Large orgs with real cross-team dependencies Program roadmap + dependency board "Dark agile" — the scaling framework re-grows the bureaucracy agile removed

04

Practices that hold regardless of model

Strip away the ceremony names and every model that actually works is leaning on the same underlying disciplines.

Definition of done

Written, shared, checked every time

Not "it compiles" — tested, reviewed, documented, and deployable. Waterfall calls this an exit criterion; Scrum calls it a DoD. Same idea.

Small batches

Shorten the loop, not the plan

A two-week sprint and a Kanban WIP limit of 3 are solving the same problem: feedback arrives before the mistake compounds.

Traceability

Requirement → code → test

A V-Model traceability matrix and a commit message with a ticket ID are the same discipline at different weights.

Debt is budgeted

Visible, not just complained about

Technical debt that isn't on the backlog isn't being managed — it's being deferred onto whoever's on call next quarter.

Blameless review

Incidents and retros ask "what," not "who"

The moment a review becomes personal, people stop reporting the near-misses that would have caught the real incident.

Docs move with code

Updated in the same change, not after

Documentation written after the fact is documentation written from memory — and memory is already wrong by then.

Review is a gate

Not a courtesy pass

Whether it's a formal design review board or a required PR approval, the point is the same: a second person can still say no.

Observability first

Built in, not bolted on after an incident

If the first time you add logging for a code path is the outage it caused, you've paid for the instrumentation twice.

05

Fit finder

Two questions place most projects: how often do requirements actually change, and how expensive is a mistake once it ships? DevOps discipline runs underneath all four quadrants — it's not a fifth option.

High stakes, known scope — V-Model or Waterfall. The cost of a wrong turn justifies the cost of planning it out first.
High stakes, unclear scope — Spiral. Spend the first loops on prototypes and risk, not on the full build.
Low stakes, known scope — Incremental or Kanban. Don't pay for ceremony the risk doesn't justify.
Low stakes, unclear scope — Scrum, XP, Lean Startup. Optimize purely for the speed of the feedback loop.
06

Failure modes worth naming

Most process failures aren't the model's fault — they're the model's form kept while its substance was dropped.

Scrummerfall Agile

Sprints are bolted onto a plan whose scope and deadline were fixed months ago. "Sprint review" becomes a status report against a schedule nobody's allowed to renegotiate.

Fix → let scope flex within the date, or the date flex within the scope. Never fix both and call it agile.

Zombie Scrum Agile

All four ceremonies happen, on schedule, every sprint — and nothing anyone says in them ever changes what happens next.

Fix → every retro item gets a named owner and a deadline, tracked exactly like a bug.

Watermelon status Any model

Green on the dashboard, red underneath. Usually caused by measuring activity — story points, hours logged — instead of outcomes.

Fix → track lead time and escaped defects alongside velocity, never velocity alone.

Cargo-cult DevOps DevOps

A green CI pipeline exists, but a manual approval gets bolted back in front of every deploy "just in case," because nobody actually trusts the test suite.

Fix → invest in the tests until the gate is trustworthy — don't just automate the ceremony around a gate nobody believes.

Dark agile Scaled agile

SAFe or LeSS is adopted to coordinate teams, and the coordination overhead it was meant to replace grows right back in the form of PI-planning committees.

Fix → scale the minimum coordination the dependency graph actually requires, not the framework's full ceremony set.

Spec-driven paralysis Plan-driven

A heavyweight requirements document gets one formal sign-off, then nobody updates it again — so the traceability matrix stops meaning anything the day coding starts.

Fix → keep the spec and its traceability matrix live and versioned, not a one-time ritual.

Applied: a three-lens stack from two of my repos

global-market-scanners and global-stock-screener each run SDLC, SAFe, and TOGAF at once — not because one wasn't enough, but because each answers a question the others don't.

LensAnswersLives in
SDLCWhat phase is this work in — and is any phase being skipped?SDLC.md phase table
SAFe (Agile)What's next, and why that over everything else in the backlog?backlog.py, WSJF ranking, PI planning
TOGAFIs the architecture still sound after everything shipped this quarter?togaf.py govern — 10/10 principles
WSJF = Cost of Delay / Job Size = (business value + time criticality + risk reduction) / job size
Highest WSJF first. In practice: a 1-point fix that clamps an absurd P/E outranks an 8-point signal build — small, urgent, and low-risk beats big and merely valuable.
Enforced, not aspirational

Definition of Done

Behaviour implemented · offline unit tests added · lint clean, dependency map regenerated · integrity & architecture governance verified · merged via PR with every CI check green. A feature isn't done until governance.py reports CONFORMANT.

SAFe artifact → repo

Backlog hierarchy

Epic = a theme ("data quality," "smart-money signals"). Feature = a shippable module. Story = a commit on a feature branch. Enabler = infra work — integrity checks, the dependency map, preflight.

The gap that closed real change

Both repos were built iteratively — each feature shipped and smoke-tested by hand — with no automated test suite and no CI. That's the exact failure this page's Universal practices section warns about: small batches with no real feedback loop underneath them.

Closing it meant adding tests/test_core.py — unit tests over the deterministic core (the rate limiter, point-in-time filing-date filtering, factor regressions) — plus a GitHub Actions workflow on every push: unit tests, architecture governance, and a file-integrity check against a committed checksum manifest. A regression now fails CI instead of shipping quietly.

Computer science theory, applied

Process models tell you how to sequence work. These are older and more fundamental — results from theory of computation, distributed systems, and information theory that hold regardless of what process you run, and quietly explain why some product and tooling decisions work and others can't.

ConceptFieldCore ideaApplied to products & tools
Conway's Law Org theory / SE A system's structure mirrors the communication structure of the org that built it An architecture problem is often an org-chart problem in disguise — redraw team boundaries before redrawing module boundaries (the "inverse Conway maneuver")
Little's Law Queueing theory WIP = throughput × time-in-system (L = λW) The arithmetic behind every WIP limit and cycle-time chart in this page's Kanban row — the only way to cut lead time without adding people is to cut work-in-progress
CAP theorem Distributed systems Under a network partition, a distributed system picks consistency or availability — never both Forces the tradeoff into the open: "cart total may lag by a second" beats an accidental tradeoff discovered during an incident review
Amdahl's Law Parallel computing Speedup from optimizing one part is capped by the share of time spent outside it Don't shave milliseconds off a hot loop that's 5% of latency when onboarding friction is 60% of churn — measure the bottleneck before funding the fix
Postel's Law Protocol design Be conservative in what you send, liberal in what you accept The right default for APIs, file importers, and form inputs alike: tolerate messy input, always emit clean, well-formed output
Computational complexity Theory of computation Cost as input size grows (Big-O) — and some problems have no known efficient exact solution An O(n²) admin screen is fine at 50 rows and a support ticket at 50,000 — and reaching for a heuristic instead of an exact solver is a legitimate product choice, not a shortcut
Undecidability Theory of computation No general algorithm can decide whether an arbitrary program halts (Turing) Sets a hard ceiling on what static analysis or automated code review can ever promise — some class of bug is provably uncatchable by any tool, which should temper how confidently a product markets its own guarantees
Shannon entropy Information theory A message's information content is inversely related to how predictable it is An alert that fires on an already-known, expected state carries zero information — it spends signal budget the reader needs for the next real incident
Mechanism design Game theory Design the payoff structure so the equilibrium behavior is the one you actually want Pricing tiers, rate limits, referral programs, reputation systems — engineer the incentive, don't rely on goodwill to get the outcome you want
Byzantine fault tolerance Distributed systems A system must tolerate participants that behave arbitrarily, not just ones that go silent Any multi-party integration — a marketplace, a plugin ecosystem, federated data — should assume a participant can be wrong or adversarial, not merely offline, and design trust boundaries accordingly

Domain-Driven Design

Where the sections above shape when work happens, DDD shapes how the codebase itself is cut up — along the boundaries of the business domain, not the technical layers. Strategic design decides where the boundaries go; tactical design is what you build inside one.

Strategic design

ConceptCore ideaApplied to products & tools
Ubiquitous languageOne vocabulary shared by domain experts and code — no separate "business term" and "code term" for the same thingA feature's name in the UI, the ticket, and the database column should be the same word; every translation between them is a chance for meaning to drift
Bounded contextAn explicit boundary where one model and its vocabulary hold true — the same word can mean something else just outside it"Order" means something different to Fulfillment than to Billing; stop forcing one shared Order object to serve both and the schema stops fighting itself
Core vs. generic subdomainNot every part of the domain deserves the same investmentSpend real design effort on the 1–2 subdomains that differentiate the product; buy or borrow the generic ones — auth, email, payments — instead of modeling them from scratch
Context mappingNaming the relationship between two bounded contexts explicitly (shared kernel, customer/supplier, conformist, anticorruption layer)Saying "we conform to the payment provider's model" out loud turns an implicit, ad hoc integration into a decision someone actually made

Tactical design

ConceptCore ideaApplied to products & tools
AggregateA cluster of objects treated as one consistency boundary, entered only through its rootStops "update three tables and hope" — an aggregate's invariants are enforced in one place, atomically
Entity vs. value objectAn entity has identity that persists through change; a value object is defined only by its attributesA user keeps identity across an edited email address; a money amount ($10, USD) doesn't — treat it as immutable and swappable, not something to mutate in place
Domain eventA fact that already happened in the domain, named in the past tense, that other parts of the system react toAn explicit OrderShipped event — not a side effect buried in a controller — is what makes a webhook, an audit log, and a notification all independently testable
Anticorruption layerA translation layer that keeps an external or legacy system's model from leaking into your ownWrap the flaky third-party API or the legacy database behind an adapter that speaks your ubiquitous language, so its quirks don't spread into your domain code

TOGAF: enterprise architecture

TOGAF treats "the architecture" as a repeatable method, not a diagram someone draws once. Its center is the Architecture Development Method (ADM) — a cycle of phases, all of them anchored to continuous Requirements Management.

Preliminary→ A · Vision→ B · Business→ C · Data & Apps→ D · Technology→ E · Opportunities→ F · Migration Plan→ G · Governance→ H · Change Mgmt↻

Cycles back to Preliminary; Requirements Management sits at the center and feeds every phase, not just phase B.

ConceptCore ideaApplied to products & tools
The ADM cycleArchitecture is a repeatable, iterated development method with defined phases, not a one-time artifactTreat "our architecture doc" as a process with an owner and a next iteration date — see this page's spec-driven paralysis anti-pattern for what happens when it isn't
BDAT domainsFour architecture layers — Business, Data, Application, Technology — addressed in that orderA technology choice justified only in technology terms, with no traceable business capability behind it, is the tell that BDAT was skipped
Architecture principlesWritten, numbered statements that constrain future decisions — not aspirationsCodified, checkable rules a build can fail against turn architecture review from a meeting into a gate
ABB vs. SBBSeparate what capability is required (Architecture Building Block) from which specific product provides it (Solution Building Block)Name the capability first — "durable message delivery" — before the vendor — "so we chose SQS" — and the decision outlives any one vendor swap
Gap analysisState the baseline architecture, state the target, and the difference between them is the migration roadmapThe fastest way to turn "we should modernize this" into funded work: write down what's there, write down what's wanted — the gap list becomes the backlog

The software testing playbook

§12's "testing strategy" row earns its own field guide: which shape of test suite fits which system, the vocabulary for what a substituted dependency actually is, the tests most teams forget exist, and the failure modes that make a green suite lie to you.

Shapes of a test suite

ShapeEmphasisBest fit
Pyramid (Cohn)Many fast unit tests, fewer integration tests, a thin layer of end-to-end tests on topLibraries and monoliths with clear, stable unit boundaries
Trophy (Kent C. Dodds)Integration tests are the largest layer; unit tests only where logic is genuinely isolatedFrontend/UI-heavy apps, where the units are trivial but the wiring between them is where bugs hide
Honeycomb (Spotify)Integration-heavy with thin unit and end-to-end layers on either sideMicroservices, where the real risk sits at service boundaries and contracts, not inside any one service

Test doubles (Fowler's taxonomy)

DoubleWhat it actually doesExample
DummyPassed to satisfy a parameter list but never actually usedA null/placeholder logger passed to a constructor that never logs in this test path
FakeA working, simplified implementation — not the real thing, but genuinely functionalAn in-memory database standing in for the real one
StubReturns canned answers to whatever calls the test makes on itA payment client stubbed to always return "approved"
SpyA stub that also records how it was called, for later assertionsAsserting the email service was called exactly once, with the right recipient
MockPre-programmed with expectations about calls, and verifies them itselfThe test fails if charge() wasn't called with the expected amount — the mock enforces it, not a later assertion

F · Fast

A slow suite stops running

If it takes coffee-break long to get feedback, people start skipping it — speed isn't a nice-to-have, it's what keeps the suite in the loop at all.

I · Isolated

No test depends on another's state

Tests must pass in any order, alone or in parallel — shared mutable state between tests is how a single failure cascades into forty red ones.

R · Repeatable

Same result, every environment

No dependence on real time, real network, or execution order — a test that passes on your machine and fails in CI is a test with a hidden dependency.

S · Self-checking

Pass/fail, no human reading a log

A test that requires a person to eyeball output and decide isn't automated — it's a manual step wearing a test's clothing.

T · Timely

Written close to the code, not after

A test written days after the code ships tests today's assumptions about what the code does, not what it was supposed to do.

Failure modes worth naming

Ice-cream-cone Inverted pyramid

Mostly manual and end-to-end tests, a thin sliver of unit tests at the bottom. Every change requires a slow, flaky, human-driven regression pass.

Fix → push coverage down the pyramid — a bug caught by a unit test costs seconds; the same bug caught by an e2e suite costs minutes and a flake investigation.

Coverage theater Metric gaming

100% line coverage with assertions that check nothing meaningful — every line executed, no behavior verified. Mutation testing exposes this; line coverage alone can't.

Fix → treat coverage as a floor that flags untested code, never a ceiling that proves quality.

Flaky-test tolerance Any suite

"Just rerun it" becomes the default response to a red build. Once that's normalized, a genuinely broken build looks exactly like noise.

Fix → quarantine flaky tests into a separate, tracked, non-blocking suite immediately — never let them sit blocking and ignored in the main one.

Testing implementation, not behavior Over-coupling

A test asserts on private internals or exact call sequences, so it breaks on every refactor even when the observable behavior never changed.

Fix → assert on inputs and outputs a caller can actually observe, not on how the code gets there.

Mocking everything Zero real integration

Every collaborator is mocked, so the suite is green while the real, unmocked wiring between components has never once been exercised.

Fix → pair unit tests (mocked) with a smaller layer of real integration tests that use the actual collaborators — that's what the Trophy and Honeycomb shapes above are for.
